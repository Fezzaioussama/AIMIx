Understand AIMIx.
From idea to agent workflow.

AIMIx is a signed-in workspace where you describe a mission, get a team of AI agents, run it in the background, and collect the deliverables. This guide connects that story to the React hooks, FastAPI functions, database entities, and LangGraph agents that make it happen.

01 / The big picture

Build

Arrange steps into stages. Give each agent a title, specialty, prompt, model, tool policy, and expected output. Save the workflow under your account, or start from a mission template.

Generate and revise

A planner model proposes a pipeline from your description. Review it, change it in a sentence, then save. The Missions screen, where sign-in lands, does all of this in one conversation.

Run in the background

Starting a run saves it and hands it to a background executor. The browser polls it, so a run can be followed live, stopped, resumed after a restart, and found in the history later.

Stay in control

A tool that can act on an outside system waits at an approval gate for its owner’s OK. A run can carry a spending limit, and every step records the tokens and cost of its model calls.

Schedule

A schedule starts runs of a saved pipeline by itself, from hourly to monthly, on a time zone’s clock, through the same run service a request uses.

Tools, files, and chat

Agents use built-in tools, the operator’s MCP servers, and each user’s own integrations. What they save lands on the Files page. A chat agent can inspect or run your workflows through tools.

Two different AI paths exist: planning (generate and revise) calls LLMProvider.generate() for a JSON definition; execution and chat build LangChain chat models and LangGraph agents that can call tools. Every new run, whether a browser request, the chat tool, or the scheduler asked for it, starts through RunService.start().

02 / Stories that explain the system

The campaign below is an illustrative workflow, not a bundled pipeline or a claim that external research tools are configured. The CRM integration in Story G is illustrative too.

Story A — Maya signs in and owns her workflows
  1. Maya registers, where the operator allows it. AuthProvider.register() calls the auth API; accounts.register() checks the password policy, hashes the password, and stores a User.
  2. She signs in. accounts.sign_in() verifies the hash; TokenSigner issues an access token, kept in memory by tokenStorage, and a rotating refresh token in an HttpOnly cookie. RequireAuth guards the screens, and sign-in lands on HOME_PATH, the Missions workspace.
  3. Each protected request carries the bearer token through client.request(); after a 401 the gateway calls refreshAccessToken() once and retries. current_user() authenticates the token and loads its user.
  4. repository.get_owned() includes the user ID in the database query, so a missing pipeline and another user’s pipeline both give a not-found error; runs, schedules, and integrations are scoped the same way.

Story B — Maya describes a mission and collects the deliverable
  1. Signed in, Maya lands on /mission (MissionPage). With no team on screen her first message is a description: useMission.send() calls useTeamGeneration.generate(), which calls generatePipeline() (Story D), and the plan appears as a draft team kept in the tab, not saved.
  2. Later messages change the team: isRunRequest() tells “run it” (whole phrases only) from a change request, which goes to useMissionProposals over useRevisePipeline (Story E). Apply replaces the team on screen.
  3. “Run it” asks for the inputs in the conversation (useMissionRun.ask()). Starting saves the team first (useMissionTeam.save()), so a new mission gets its address, /mission/{id}, and then calls startRun().
  4. useFollowedRun polls the newest run: the Team pane draws the graph with live statuses, and the Results pane shows Deliverables as each output step is saved, RunDetails (a LiveRun), and RecentFiles. Leaving never stops the run, and reopening /mission/{id} loads the pipeline and its newest run (useLatestRun). The conversation lives in the tab (sessionStorage); the team and its runs live on the server.

Story C — Maya builds a campaign pipeline manually
  1. In PipelineBuilderPage, she adds a “Key facts” agent in stage 1, “Email” and “Social post” agents in stage 2, and an “Editor” in stage 3.
  2. usePipelineBuilder owns the editable definition. Its actions insert steps, change roles and prompts, and mark unsaved edits dirty.
  3. savePipeline() creates a new pipeline or replaces an existing one. Pydantic validates the request; create_with_steps() or replace_steps() commits the definition.
  4. She runs the saved definition on a product brief, typed or attached (AttachDocument: extract_document() reads PDF, Office, image, and text files on the server, with OCR for scans). The builder requires a saved, clean pipeline, so edits must be saved before running.
  5. usePipelineBuilder.run() starts a background run that the page follows with useFollowedRun: PipelineRunView shows live step statuses and each output as soon as it is saved, and FollowedRunBar holds Stop, Resume, and Open in Runs. OutputCard shows the text and input used; ToolCallTrace shows tool names and statuses.

Story D — Maya asks AI to propose the workflow
  1. useAutoPipeline.generate() sends a description and planner model through generatePipeline().
  2. generate_pipeline() obtains tool descriptors from PipelineToolCatalog.available_sync(): built-in tools, the operator’s MCP tools, and her own integrations’ tools.
  3. pipeline_service.generate() calls pipeline_generation_prompt(), then ask_planner(), which calls provider.generate().
  4. parse_plan() extracts JSON and rejects missing or malformed steps. sanitise_step() renumbers orders, normalises stage, title, role, and output flags, and repairs unknown models or tool selections.
  5. The proposed definition is returned without being saved. Maya edits it and saves; subsequent saves update the saved proposal. A mission template skips the planner: use_template() runs its steps through the same sanitise_step() and saves them as her own pipeline.

Story E — Maya changes a pipeline in a sentence
  1. In the builder, or under a generated plan, RevisePanel takes “Add an SEO agent that works alongside the marketing agent”. useRevisePipeline.propose() sends the current draft, saved or not, through revisePipeline().
  2. revise_pipeline() validates the draft with PipelineDraftIn (a blank name or prompt is allowed) and the instruction, then obtains the same tool descriptors as generation.
  3. pipeline_revision.revise() renders pipeline_revision_prompt() (the shared planner guide, the revision rules, and the draft and instruction fenced as data) and calls ask_planner(), the call-and-parse path generation uses.
  4. diff_pipelines() compares the draft with the sanitised revision and returns the change list.
  5. RevisionReview shows the changes in plain words and a diagram preview. Apply replaces the draft and marks it unsaved; nothing is saved until Maya saves.

Story F — Maya asks chat to inspect or run a saved pipeline
  1. useChatStream.send() appends a user message and empty assistant reply. streamChatReply() opens a streaming POST through streamText().
  2. The chat endpoint calls stream_reply(), which obtains the first text chunk before committing the HTTP streaming response.
  3. LangGraphChatAgent builds an agent with the native tools, the built-in toolbox, and the MCP tools she may reach; the model chooses whether to call a tool. list_pipelines, inspect_pipeline, and run_pipeline are bound to the authenticated user; run_pipeline goes through the run service, so the run is saved like any other, marked as started from chat, and the tool waits for its end.
  4. Chat has no run to pause, so guard_tools() leaves out every tool that must ask first (by default, every MCP tool). The agent streams model text through a queue; the frontend appends chunks, and unmounting the chat screen aborts the request.

The visible chat transcript lives in React state. The current request sends the prompt only; it does not send the full conversation history.

Story G — A run asks Maya’s permission before a tool acts
  1. Maya connects her CRM under Settings → Integrations (IntegrationsSection); “Ask me before its tools act” is on by default.
  2. A step uses one of its tools. guard_tools() has put ApprovalMiddleware in front of it, so RunApprovalGate.ask() saves a RunApproval (pending) and moves the run to waiting in one transaction, then reads the row every APPROVAL_POLL_SECONDS, sleeping between reads so other runs go on.
  3. Polling shows pending_approvals: PendingApprovals renders an ApprovalCard, and the Runs tab shows an amber count (useWaitingRuns).
  4. Maya approves: decisions.answer() settles the request with a compare-and-set from pending, the gate reads approved, the tool runs, and the run is running again. Decline, or no answer within APPROVAL_TIMEOUT_SECONDS, gives the agent an error result and the run goes on.

backend/api/services/approvals/gate.py · decisions.py

Story H — Maya resumes a run that a restart interrupted
  1. A deploy restarts the server while her run is in stage 2. On shutdown the executor cancels its jobs and RunService._execute() records interrupted; after a crash, interrupt_abandoned_runs() does the same at startup. Running steps become cancelled.
  2. The run shows “Interrupted” with Resume: useRun.resume() posts to /api/runs/{id}/resume, and RunService.resume() queues the run again, resetting only the steps that did not succeed.
  3. The job runs the run’s own saved definition. _plan() puts the succeeded steps into RunControl.completed, so the graph returns their saved results without calling their agents and work continues from the first stage that did not fully succeed.
  4. The resumed run uses the requester’s current model settings, and asks for approvals again.

Story I — A schedule starts the run on Monday morning
  1. In the builder’s “Schedule this pipeline” panel (SchedulePanel) Maya picks weekly, Monday, 09:00, Paris time. The form’s “next run” comes from POST /api/schedules/preview, the server’s next_run_after(), so daylight saving is decided in one place; saving checks the pipeline and its inputs with prepare_run(), validates the timing (checked()), and stores next_run_at in UTC.
  2. The app’s lifespan started a SchedulerLoop thread. Every SCHEDULER_TICK_SECONDS it calls Scheduler.tick(), which lists the due schedules.
  3. For each, claim() moves next_run_at to the first time after now, a compare-and-set only one caller wins: two ticks or processes start one run between them, and a schedule overdue after downtime runs once.
  4. The winner resolves the owner’s LLM profile (ProfileAgents) and calls RunService.start() with the trigger schedule: an ordinary background run, tagged “Scheduled” in the history. If it cannot start (no API key, inputs that no longer fit), the reason is saved as last_error.

Story J — A spending limit stops a run
  1. Maya types a limit in the run form (CostLimitField); runRequest() sends it as max_cost_usd and RunService.start() saves it on the run (a limit left unset takes RUN_DEFAULT_MAX_COST_USD). _execute() builds a RunMeter from it and hands each step its meter through RunControl.
  2. Before every model call the step’s UsageCallback asks RunMeter.check(); after it, the call’s tokens and cost join the shared total and, through RunRecorder.record_usage(), the step’s row.
  3. Once the total reaches the limit, check() raises BudgetExceeded: the step fails with budget_exceeded, LangGraph cancels the parallel steps, and the run ends failed. Finished steps keep their outputs; calls already in flight still finish and count.
  4. The status bar says “Spending limit reached.” and ResumeControl asks for a higher limit, because ensure_room() refuses a resume under a limit already reached. Usage also shows under Settings → Usage (usage_report(), GET /api/usage).

backend/api/services/run_budget.py · backend/llm/usage.py

03 / Follow one pipeline execution

Use the walkthrough controls to trace the call chain. Without JavaScript, the complete ordered trace remains visible below.

  1. UI → hook → gateway. usePipelineBuilder.run(draft) (or useMissionRun.start()) calls core/api/runs.startRun(id, body); runRequest() builds the body, with an optional cost limit. request() adds the bearer token and a 30 s default timeout: the call starts the run, it does not wait for it.
  2. Validate and resolve dependencies. POST /api/pipelines/{id}/runs is endpoints.runs.start_run(). RunRequest trims the inputs and validates the optional limits (BudgetIn). PipelineRunContext bundles the user, session, agent factory, and RunService; get_owned() loads the pipeline, or answers 404.
  3. Check, snapshot, and save. RunService.start() calls prepare_run(): ensure_runnable(), snapshot_pipeline() into immutable PipelineSpec and StepSpec values, and bind_run_inputs(). A wrong input is a 400 and nothing is saved. Then repository.create() saves a queued Run (the snapshot as JSON through spec_to_json(), plus its limits) with one pending RunStep per step.
  4. Hand off, answer, and wait for a slot. RunService submits _execute to the RunExecutor and the endpoint answers 202 with the run; the page starts polling (followed.follow(), useRun.adopt()). BackgroundRunExecutor is one asyncio loop on a daemon thread (aimix-runs) whose semaphore lets RUN_MAX_CONCURRENT jobs execute. When the job starts, RunRecorder.begin() moves queued to running with a compare-and-set, so a run stopped while it waited never starts.
  5. Rebuild the plan and construct the graph. _execute() reads the run’s own snapshot (spec_from_json()), binds its inputs again, collects the steps an earlier attempt finished (completed), and builds a RunMeter from the run’s limits and spending; a RunControl carries them with the recorder as its observer. GraphPipelineRunner.arun() then adds one agent node per step and a join node after every stage (_build_graph()). A step found in completed returns its saved result without running its agent: that is how a resumed run skips finished work.
  6. Execute each agent and report it. _agent_node() fills the prompt with step_prompt() and creates an AgentTask carrying the step’s meter and its place in the run. _run_step() tells the observer the step started, and RunRecorder.on_step_event() marks its row running, each event in its own short transaction. PipelineAgentGenerator.execute() builds the model, tools, approval policy, and gate for this user.
  7. Model ↔ tools loop. LangGraphStepAgent.reply() resolves the tool policy with resolve_tools(), lets guard_tools() put the approval gate in front of tools that ask first, wraps the model with metered(), and runs create_agent() under timeout and recursion limits. The role becomes a system prompt.
  8. Budget and approval checkpoints. Before every model call the UsageCallback asks RunMeter.check(); once a limit is reached it raises BudgetExceeded and the step fails with budget_exceeded. After each call the usage joins the run’s total and, through RunRecorder.record_usage(), the step’s row. A gated tool call stops at RunApprovalGate.ask(): a pending RunApproval is saved, the run becomes waiting, and the step polls the database until the owner approves or declines, or the request expires.
  9. Finish the step and merge. The agent returns an AgentOutcome (text, tool traces, usage) that the graph turns into a StepResult; the observer hears succeeded, and the row gets its output and tool calls (or failed with the error code, or cancelled). Parallel nodes write results into a reducer-backed map; _join_node() calls merge_stage_outputs(): one result passes through, several are labelled by step order.
  10. End the run. After the last join the runner marks deliverables with output_orders() and returns a RunResult; _execute() records succeeded with the final text. A DomainError from any step ends the run failed with its code and detail; a cancellation from shutdown ends it interrupted. Each ending is a compare-and-set, so a run its owner already stopped stays cancelled.
  11. Poll and display. While the run is queued, running, or waiting, useRun calls getRun() every RUN_POLL_INTERVAL_MS (1.5 s). GET /api/runs/{id} reads the run with its steps and pending approvals (another user’s run is a 404), and LiveRun hands them to PipelineRunView: live node statuses, each output as soon as it is saved, cost and elapsed time, approval cards, and Stop or Resume. Polling stops when the run ends.
Output does not mean “stop”. Marked output steps still feed later stages. If any steps are marked, those are deliverables; otherwise all steps in the final stage are deliverables. final_output is the final stage’s merged text, which may differ from the set of marked deliverables.
Who writes a run. Every status change is a compare-and-set in repositories/runs.py, so a request thread and the executor never overwrite each other; a run’s state is its database rows, not a LangGraph checkpoint. queued, running, and waiting are active (ACTIVE_RUN_STATUSES: can be stopped, not deleted); failed, cancelled, and interrupted can be resumed (RESUMABLE_RUN_STATUSES); succeeded is final.

Persisted data versus runtime data

User ─┬ owns Pipeline ─ PipelineStep
      ├ owns Run ─┬ RunStep
      │           └ RunApproval
      ├ owns Schedule ─ starts a Run
      └ owns Integration (MCP server)

Pipeline ─ snapshot_pipeline() ─►
  PipelineSpec ─ StepSpec
  ─ spec_to_json() ─► Run.definition
  ─ spec_from_json() ─► the graph
graph + StepAgent ─► StepEvent
  ─ RunRecorder ─► RunStep rows
graph ─► RunResult ─ StepResult
  ─ ToolCallTrace

Saved steps hold order, stage, title, role, prompt, model, allowed_tools, is_output, and expected_output. Order identifies a step; stage determines when it runs. The database enforces unique order within a pipeline and cascades deletion to its steps.

A run copies the definition as JSON, so editing or deleting the pipeline later changes nothing about it. Run steps keep status, input used, output, tool-call names and statuses (never arguments or results), error, times, tokens, and cost; a run’s totals are computed from its steps. Chat messages have no table: the chat transcript lives in React state, the mission conversation in the tab’s sessionStorage.

Tool policy is a three-way contract

null

All tools available to this agent: native tools (pipeline inspection and the enabled built-ins) plus the operator’s MCP tools and the user’s enabled integrations.

[]

No tools. Resolution returns immediately without MCP discovery.

[names]

Only selected tools. Native-only selections avoid MCP discovery; a selected tool that cannot be found (an integration that is down, say) raises tool_unavailable.

Pipeline agents receive the native inspection tools and the enabled built-ins, not the native pipeline-running tool; chat receives run_pipeline too. MCP tools can act on outside systems, so in a run the tools of MCP servers and integrations ask their owner first (the approval policy decides), and chat is not offered them.

06 / Failure paths and current behavior

Boundary failures

Invalid requests fail schema validation, and a run’s inputs are checked before anything is saved. Missing or expired tokens fail authentication after one refresh attempt. Ownership-aware lookup prevents access to another user’s pipelines, runs, schedules, and integrations.

AI and tool failures

Invalid planner JSON raises UpstreamResponseInvalid. Timeout, provider, recursion, and MCP failures map to domain errors. In a run, a failed step ends the run failed, a parallel step still working is cancelled, and finished steps keep their outputs.

One error contract

api/errors.py shapes HTTP errors as {"error": "code", "detail": "message"}. The browser gateway turns failed JSON requests into ApiError; a failed run carries the same code and detail in its error.

When a run does not simply succeed

Interrupted or stopped

On shutdown the executor cancels its jobs and each running one records interrupted, unless its owner stopped it first (RunService.cancel() writes cancelled). After a crash, or for a run still waiting for a slot, interrupt_abandoned_runs() does it at the next start. Running steps become cancelled, pending approvals expired. Either can be resumed: finished steps are reused and approvals are asked again. Nothing resumes by itself.

Approval declined or expired

Declined: decisions.answer() settles the request, the tool does not run, and the agent gets an error result (“The user declined this action…”) and goes on; the step’s trace shows error, the run does not fail. Expired: nobody answered within APPROVAL_TIMEOUT_SECONDS, or the run stopped or restarted. A late answer is a 409 conflict. A scheduled run has nobody watching, so a call that asks usually expires.

Spending limit reached

RunMeter.check() refuses the next model call: the step fails with budget_exceeded and the run ends failed, finished steps kept; a call in flight still finishes and counts. Resume needs a higher limit (409 budget_exceeded under the same one). A cost limit cannot stop a model with no known price; a token limit can.

Scheduler claims

claim() moves next_run_at only while it still equals the time the tick saw, so one process starts each occurrence and an overdue schedule runs once; a process that dies after the claim, before the run is saved, loses that occurrence. A start that cannot happen is saved as last_error and the loop goes on.

A failing integration

discover_tools() skips an integration it cannot reach (logged as integration.discovery_skipped), so work that does not need it continues; a step that selected one of its tools fails in resolve_tools() with tool_unavailable. An operator MCP server that fails fails discovery for everyone. A built-in tool that fails returns an error result the agent can react to; a failing MCP call stops the run.

Provider failures

llm/retry.py retries connection failures and the statuses 408, 429, 500, 502, 503, and 504, at most LLM_MAX_RETRIES times, with jittered backoff or the provider’s Retry-After. Timeouts and other statuses fail at once, and tool calls are never retried. The last failure surfaces as a domain error such as provider_unavailable or provider_timeout.

  • Streaming errors change after the first chunk. Before streaming starts, a domain error can become a normal HTTP error. Afterward, stream_reply() logs a domain failure and ends the stream; it does not send a structured error event.
  • Runs live in one process. The executor’s queue and the scheduler run inside the API process, so the app deploys as one worker. A restart interrupts running runs, and progress is polled, not pushed.
  • Limits come from configuration. Provider timeouts and retries, agent timeouts, recursion, MCP timeouts, PIPELINE_MAX_PARALLEL_STEPS, and RUN_MAX_CONCURRENT are configured in backend settings. Consult the environment example for defaults.
  • The browser retries once. After a 401 the gateway calls refreshAccessToken() and repeats the request; if that fails it clears the token and the route guard sends the user to sign in. A failed run poll is tried again; a 404 is not.
  • Markdown is a trust boundary. Model output passes through renderMarkdown sanitisation before HTML presentation.
