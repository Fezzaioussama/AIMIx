Understand AIMIx.
From idea to agent workflow.

AIMIx is a signed-in workspace for building, generating, and running AI pipelines. This guide connects the user’s story to the React hooks, FastAPI functions, database entities, and LangGraph agents that make it happen.

01 / The big picture

Build

Arrange steps into stages. Give each agent a title, specialty, prompt, model, and tool policy. Save the workflow under your account.

Generate

Describe a workflow. A planner model proposes a pipeline using the model and tool catalogues. Review and edit the proposal before saving.

Run or chat

Supply input to a saved pipeline and inspect its deliverables. Alternatively, ask the chat agent to inspect or run your workflows through tools.

Two different AI paths exist: planning calls LLMProvider.generate() for a JSON definition; execution and chat build LangChain chat models and LangGraph agents that can call tools.

02 / Stories that explain the system

The campaign below is an illustrative workflow, not a bundled pipeline or a claim that external research tools are configured.

Story A — Maya signs in and owns her workflows
  1. Maya registers. AuthProvider.register() calls the auth API; accounts.register() checks the password policy, hashes the password, and stores a User.
  2. She signs in. accounts.sign_in() verifies the hash and uses TokenSigner to issue access and refresh tokens. tokenStorage stores them, and RequireAuth guards the screens.
  3. Each protected request carries a bearer token through client.request(). current_user() authenticates the token and loads its user.
  4. repository.get_owned() includes the user ID in the database query. A missing pipeline and another user’s pipeline both produce a not-found error.

frontend/src/core/auth/AuthContext.tsx · backend/api/services/accounts.py · backend/api/deps.py · backend/api/repositories/pipelines.py

Story B — Maya builds a campaign pipeline manually
  1. In PipelineBuilderPage, she adds a “Key facts” agent in stage 1, “Email” and “Social post” agents in stage 2, and an “Editor” in stage 3.
  2. usePipelineBuilder owns the editable definition. Its actions insert steps, change roles and prompts, and mark unsaved edits dirty.
  3. savePipeline() creates a new pipeline or replaces an existing one. Pydantic validates the request; create_with_steps() or replace_steps() commits the definition.
  4. She runs the saved definition on a product brief. The builder requires a saved, clean pipeline, so edits must be saved before running.
  5. PipelineRunView presents outputs, all step results, and timing. OutputCard shows the text and input used; ToolCallTrace shows tool names and statuses.

frontend/src/features/pipelines/usePipelineBuilder.ts · frontend/src/core/api/pipelines.ts · backend/api/endpoints/pipelines.py

Story C — Maya asks AI to propose the workflow
  1. useAutoPipeline.generate() sends a description and planner model through generatePipeline().
  2. generate_pipeline() obtains tool descriptors from PipelineToolCatalog.available_sync().
  3. pipeline_service.generate() calls pipeline_generation_prompt(), then provider.generate().
  4. parse_plan() extracts JSON and rejects missing or malformed steps. _sanitise_step() renumbers orders, normalises stage, title, role, and output flags, and repairs unknown models or tool selections.
  5. The proposed definition is returned without being saved. Maya edits it and saves; subsequent saves update the saved proposal. Full persistence validation still happens at the save boundary.

frontend/src/features/pipelines/useAutoPipeline.ts · backend/api/services/pipelines.py · backend/api/services/prompts.py · backend/api/services/tool_catalog.py

Story D — Maya asks chat to inspect or run a saved pipeline
  1. useChatStream.send() appends a user message and empty assistant reply. streamChatReply() opens a streaming POST through streamText().
  2. The chat endpoint calls stream_reply(), which obtains the first text chunk before committing the HTTP streaming response.
  3. LangGraphChatAgent builds an agent with native tools and configured MCP tools. The model chooses whether to call a tool.
  4. Native chat tools include list_pipelines, inspect_pipeline, and run_pipeline. They are bound to the authenticated user; running reuses the pipeline service and step-agent factory.
  5. The agent streams model text through a queue; the frontend appends chunks. Unmounting the chat screen aborts the request.

frontend/src/features/chat/useChatStream.ts · backend/api/services/chat.py · backend/api/services/agent.py · backend/api/services/agent_tools.py

The visible chat transcript lives in React state. The current request sends the prompt only; it does not send the full conversation history.

03 / Follow one pipeline execution

Use the walkthrough controls to trace the call chain. Without JavaScript, the complete ordered trace remains visible below.

  1. UI → hook → gateway. usePipelineBuilder.run(input) calls core/api/pipelines.runPipeline(id, input). request() supplies auth headers and the generation timeout, then waits for JSON.
  2. Validate and resolve dependencies. RunRequest rejects blank input. PipelineRunContext bundles the authenticated user, database session, and user-bound agent factory.
  3. Load and snapshot. endpoints.run_pipeline() loads the owned pipeline and calls ensure_runnable(). services.run() maps ORM entities through snapshot_pipeline() to immutable PipelineSpec and StepSpec values.
  4. Construct the graph. GraphPipelineRunner.run() bridges to async arun(). _group_by_stage() sorts by stage and order. _build_graph() adds one agent node per step and a join node after every stage.
  5. Execute each agent. _agent_node() substitutes the current input with step_prompt() and creates an AgentTask. PipelineAgentGenerator.execute() constructs the selected model, user-bound tools, and runtime limits.
  6. Model ↔ tools loop. LangGraphStepAgent.reply() resolves the tool policy and uses create_agent(). The role becomes a system prompt. The agent runs under timeout and recursion limits and returns an AgentOutcome with text and tool traces.
  7. Merge and advance. Parallel nodes write StepResult values into a reducer-backed results map. _join_node() calls merge_stage_outputs(): one result passes through; multiple results are labelled by step order.
  8. Shape and display results. The runner marks deliverables and returns RunResult. The endpoint converts it to RunResponse. The hook stores intermediate_results and client-measured elapsed time for PipelineRunView.
Output does not mean “stop”. Marked output steps still feed later stages. If any steps are marked, those are deliverables; otherwise all steps in the final stage are deliverables. final_output is the final stage’s merged text, which may differ from the set of marked deliverables.

backend/api/services/multiagent/graph.py · backend/api/services/multiagent/mapper.py · backend/api/services/multiagent/step_agent.py

Persisted data versus runtime data

User 1 ── owns ── * Pipeline 1 ── contains ── * PipelineStep
                        │ snapshot_pipeline()
                        ▼
                   PipelineSpec ── StepSpec
                        │ GraphPipelineRunner + StepAgent
                        ▼
                     RunResult ── StepResult ── ToolCallTrace

Saved steps hold order, stage, title, role, prompt, model, allowed_tools, and is_output. Order identifies a step; stage determines when it runs. The database enforces unique order within a pipeline and cascades deletion to its steps.

Runs and chat messages have no dedicated persistence models in the current code. Execution results are returned to the client; they are not saved as a run-history table.

Tool policy is a three-way contract

null

All tools available to this agent: native tools plus configured MCP tools.

[]

No tools. Resolution returns immediately without MCP discovery.

[names]

Only selected tools. Native-only selections avoid MCP discovery; unavailable selected tools raise a domain error.

Pipeline agents receive the native inspection tools, not the native pipeline-running tool. Chat receives inspection and execution tools. Configured MCP tools can have their own capabilities; “read-only native tools” does not imply that every MCP tool is read-only.

06 / Failure paths and current behavior

Boundary failures

Invalid requests fail schema validation. Missing or expired tokens fail authentication. Ownership-aware lookup prevents access to another user’s pipelines.

AI and tool failures

Invalid planner JSON raises UpstreamResponseInvalid. Runtime timeout, provider, recursion, and MCP failures map to domain errors. A failed stage does not return a successful partial run response.

One error contract

api/errors.py shapes HTTP errors as {"error": "code", "detail": "message"}. The browser gateway turns failed JSON requests into ApiError.

  • Pipeline generation and runs wait for completion. They currently return one JSON response; there is no run polling endpoint or progressive step stream. Chat uses a plain-text stream.
  • Streaming errors change after the first chunk. Before streaming starts, a domain error can become a normal HTTP error. Afterward, stream_reply() logs a domain failure and ends the stream; it does not send a structured error event.
  • Limits come from configuration. Provider timeouts, agent timeouts, recursion, MCP timeouts, and pipeline concurrency are configured in backend settings. Consult the environment example for defaults.
  • Refresh support exists on the backend. The frontend gateway clears tokens on a 401; it does not transparently refresh and retry that request.
  • Markdown is a trust boundary. Model output passes through renderMarkdown sanitisation before HTML presentation.

07 / A practical reading path

  1. Start with the screen: read App.tsx, then PipelineBuilderPage and usePipelineBuilder to connect buttons with actions.
  2. Cross the network: read the pipeline API module, gateway, endpoint, and request/response schemas.
  3. Follow the execution: read services/pipelines.py, the snapshot mapper, contracts, graph, and step-agent adapter.
  4. Explore capabilities: read agent_runtime.py, agent_tools.py, tool discovery, and model factories.
  5. Learn from tests: graph tests cover stage ordering, fan-out/join, and outputs; agent/tool tests cover policies and failures; endpoint and database tests cover auth, ownership, contracts, and migrations.

Local development: make install installs dependencies; make run-aimix starts the app (backend startup applies migrations). Use make format and make check for the repository’s quality gates. Read the setup guide before configuring credentials.
